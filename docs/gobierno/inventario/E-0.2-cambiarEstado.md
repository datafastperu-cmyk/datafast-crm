```typescript
  [EstadoContrato.PENDIENTE_ACTIVACION]: [EstadoContrato.ACTIVO, EstadoContrato.BAJA_DEFINITIVA],
  [EstadoContrato.ACTIVO]:               [EstadoContrato.SUSPENDIDO, EstadoContrato.BAJA_DEFINITIVA],
  [EstadoContrato.SUSPENDIDO]:           [EstadoContrato.ACTIVO, EstadoContrato.BAJA_DEFINITIVA],
  // CORTADO se queda sin orígenes y sin destinos: retirado el 2026-08-09 (fase 1). Sin ninguna
  // transición que lleve a él, el estado es inalcanzable aunque el valor siga vivo en el enum
  // de PostgreSQL — el mismo trato que recibió MOROSO.
  [EstadoContrato.CORTADO]:              [],
  [EstadoContrato.BAJA_DEFINITIVA]:      [],
};

// Guardas de negocio por transición — condición que debe cumplirse además de la transición válida.
// Se evalúan solo cuando !automatico && !adminOverride.
//
// H-7 (2026-08-09): las dos guardas de reactivación leían `c.deudaTotal` —la deuda TOTAL— y por
// tanto un comprobante emitido y aún sin vencer impedía devolver el servicio a un abonado que
// acababa de pagar todo lo que debía. Ahora reciben la deuda **vencida**, con la única definición
// que hay (`DeudaPorContratoService.vencidaQueBloquea`), la misma que usa la reactivación
// automática al registrar un pago. Antes eran dos criterios distintos para la misma pregunta, y
// los dos estaban mal.
interface ContextoGuarda {
  contrato: Contrato;
  /** Deuda VENCIDA e impaga. No es `contrato.deudaTotal`, que incluye lo aún no vencido. */
  deudaVencida: number;
}

type GuardaFn = (ctx: ContextoGuarda) => string | null; // null = pasa, string = mensaje de error

const bloqueaReactivacion = ({ deudaVencida }: ContextoGuarda): string | null =>
  deudaVencida > 0
    ? `Deuda vencida S/ ${deudaVencida.toFixed(2)} — use adminOverride para forzar`
    : null;

const GUARDAS: Partial<Record<string, GuardaFn>> = {
  [`${EstadoContrato.SUSPENDIDO}->${EstadoContrato.ACTIVO}`]: bloqueaReactivacion,
  [`${EstadoContrato.ACTIVO}->${EstadoContrato.SUSPENDIDO}`]:
```

## 3. Escrituras, en el orden real de ejecución

Los ocho `dataSource.query()` van sin transacción: **cada escritura hace autocommit por
separado**. No hay punto de reversión.

```
cambiarEstado(id, dto, user, automatico, req)
│
├─ 0. findOne()                                    ── LEE servicios
├─ 1. si !automatico → TRANSICIONES + GUARDAS
│     └─ DeudaPorContratoService.vencidaQueBloquea() ── LEE facturas
│
├─ 2a. si ACTIVO ← SUSPENDIDO
│      ├─ setImmediate (fuera del request, sin esperar)
│      │    ├─ LEE routers
│      │    ├─ FirewallService.reactivarCliente()      → MikroTik: quita de address-list
│      │    ├─ PppoeService.setEstado(false)           → MikroTik: habilita secret
│      │    └─ si falla → ESCRIBE comandos_red_pendientes (REACTIVAR)
│      ├─ XuiLinesService.habilitarLineDeContrato()  ── ESCRIBE xui_lines (sin esperar)
│      └─ LEE clientes → emit notification.servicio.reactivado
│
├─ 2b. si BAJA_DEFINITIVA
│      ├─ SagaLogService.iniciar()                  ── ESCRIBE saga_log
│      ├─ S1 liberarIp()                            ── ESCRIBE ips_asignadas
│      │       + registrarPaso                      ── ESCRIBE saga_log
│      ├─ S2 desaprovisionarOlt()      [20 s]       → SmartOLT   + ESCRIBE saga_log
│      ├─ S2b encolarDesaprovisionarOnu()           ── ESCRIBE comandos_red_pendientes
│      │                                               (solo si hay ftth_onu_registro vivo)
│      ├─ S3 desaprovisionarMikrotik() [25 s]       → MikroTik   + ESCRIBE saga_log
│      │       si falla → ESCRIBE comandos_red_pendientes (DESPROVISIONAR)
│      ├─ S4 eliminarDeAccessListAntena() [15 s]    → antena AP  + ESCRIBE saga_log
│      ├─ S5 eliminarLineDeContrato()  [15 s]       ── ESCRIBE xui_lines + saga_log
│      ├─ SagaLogService.completar()                ── ESCRIBE saga_log
│      └─ UPDATE clientes SET nota_baja             ── ESCRIBE clientes  (tabla ajena)
│
├─ 3. ContratoRepository.update()                   ── ESCRIBE servicios        ← el estado
├─ 4. ContratoRepository.guardarHistorial()         ── ESCRIBE servicios_historial
├─ 5. AuditoriaService.logUpdate()                  ── ESCRIBE auditoria_logs
│
├─ 6. si SUSPENDIDO → UPDATE clientes               ── ESCRIBE clientes  (tabla ajena)
│      └─ INSERT clientes_historial_estados         ── ESCRIBE clientes_historial_estados
├─ 7. si ACTIVO←SUSPENDIDO → UPDATE clientes        ── ESCRIBE clientes  (tabla ajena)
│      └─ INSERT clientes_historial_estados         ── ESCRIBE clientes_historial_estados
├─ 8. si BAJA && !automatico → UPDATE clientes      ── ESCRIBE clientes  (tabla ajena)
│      └─ INSERT clientes_historial_estados         ── ESCRIBE clientes_historial_estados
│
├─ 9. si SUSPENDIDO
│      ├─ setImmediate (fuera del request, sin esperar)
│      │    ├─ LEE routers + clientes
│      │    ├─ FirewallService.suspenderCliente()      → MikroTik: mete en address-list
│      │    ├─ PppoeService.desconectarSesion()        → MikroTik: corta la sesión viva
│      │    ├─ PppoeService.setEstado(true)            → MikroTik: deshabilita secret
│      │    └─ si falla → ESCRIBE comandos_red_pendientes (SUSPENDER)
│      ├─ XuiLinesService.deshabilitarLineDeContrato() ── ESCRIBE xui_lines (sin esperar)
│      └─ LEE clientes+empresas → emit notification.servicio.suspendido
│                                    └─→ OutboxRedService escribe comandos_red_pendientes
│                                        (SUSPENDER_ONU)  ← así llega la orden a la OLT
│
└─ 10. si BAJA_DEFINITIVA → softDelete()            ── ESCRIBE servicios (deleted_at)
        return Object.assign(contrato, upd)
       si no → return this.findOne()                ── LEE servicios
```

**Tablas escritas (9):** `servicios`, `servicios_historial`, `clientes`,
`clientes_historial_estados`, `saga_log`, `ips_asignadas`, `xui_lines`,
`comandos_red_pendientes`, `auditoria_logs`.

De ellas, **cuatro no le pertenecen** según el manifiesto PA-12: `clientes`,
`clientes_historial_estados` (dueño `clientes`), `ips_asignadas` (dueño `mikrotik`) y
`comandos_red_pendientes` (dueño `outbox-red`).

### La asimetría que importa

La suspensión toca el hardware **después** de escribir la base (paso 9); la reactivación lo
toca **antes** (paso 2a). Y las dos lo hacen dentro de un `setImmediate`, es decir **fuera del
request**: la respuesta HTTP se devuelve sin saber si el router obedeció. La única red de
seguridad es el `catch` que encola en el outbox — y ese `catch` solo cubre la excepción, no el
caso en que el comando se aplique a medias.

## 4. Estados y transiciones

| Origen | Destinos legales |
|---|---|
| `pendiente_activacion` | `activo`, `baja_definitiva` |
| `activo` | `suspendido`, `baja_definitiva` |
| `suspendido` | `activo`, `baja_definitiva` |
| `cortado` | **ninguno** (inalcanzable desde 2026-08-09) |
| `baja_definitiva` | **ninguno** (terminal) |

Guardas adicionales, evaluadas solo si `!automatico && !dto.adminOverride`:

| Transición | Guarda | Mensaje |
|---|---|---|
| `suspendido → activo` | `deudaVencida > 0` bloquea | «Deuda vencida S/ N — use adminOverride para forzar» |
| `activo → suspendido` | prórroga vigente bloquea | «Prórroga activa hasta F — use adminOverride para suspender antes» |

`moroso` y `cortado` siguen existiendo en el enum de PostgreSQL pero ninguna transición lleva
a ellos.

### La máquina de estados no gobierna a las máquinas

```typescript
if (!automatico) {
  //  ↑ TODA la validación —transiciones y guardas— vive dentro de este if
}
```

Con `automatico = true` se saltan **las dos cosas**: la tabla de transiciones y las guardas de
negocio. Los cinco invocadores que pasan `true` son:

| Quién | Transición que fuerza | Por qué |
|---|---|---|
| `ClientesService.terminarContratosCliente()` | → `baja_definitiva` | cascada cliente → servicios |
| `ClientesService.suspenderContratosCliente()` | → `suspendido` | cascada cliente → servicios |
| `ClientesService.reactivarContratosCliente()` | → `activo` | cascada cliente → servicios |
| `ClientesService.onboarding()` (rollback) | → `baja_definitiva` | deshacer un alta fallida |
| `PagosService.verificarYReactivarContrato()` | → `activo` | reactivación por pago |

El caso de `pagos` es el relevante: reactiva **sin comprobar la deuda vencida**, porque él ya
la comprobó antes de llamar. Pero eso significa que la guarda no es una garantía del recurso,
sino una cortesía hacia el operador humano. Un flujo automático puede llevar un servicio de
`cortado` a `activo` aunque `cortado` no tenga ninguna transición declarada.

## 5. Qué devuelve

**Firma:** `Promise<Contrato>` — un objeto, nunca `ResultadoOperacion`.

| Camino | Qué devuelve |
|---|---|
| Éxito general | `this.findOne(id, empresaId)` — el contrato releído de la base |
| Éxito en baja definitiva | `Object.assign(contrato, upd)` — el objeto **en memoria**, porque la fila ya tiene `deleted_at` y `findOne` no la encontraría |
| Transición ilegal | lanza `BadRequestException` |
| Guarda incumplida | lanza `BadRequestException` |
| Contrato inexistente | lanza lo que lance `findOne` (`NotFoundException`) |
| **Fallo de MikroTik** | **no se refleja**: ocurre en `setImmediate`, ya se devolvió la respuesta |
| **Fallo de IPTV** | **no se refleja**: `.catch()` que solo escribe un `warn` |
| **Fallo de OLT en la baja** | **no se refleja**: `withTimeout(...).catch()` marca el paso `FAIL` en la saga y continúa |

Consecuencia directa: **el valor de retorno no distingue «aplicado» de «aceptado, sin
confirmar»**. Un `200 OK` con el contrato en `suspendido` es compatible con un router que
nunca se enteró. Es exactamente el vacío que `ResultadoOperacion` existe para cubrir, y este
método —el más importante del Core— no lo usa.

## 6. Eventos y trabajos que dispara

| Evento | Cuándo | Consumidores | Qué hace el consumidor |
|---|---|---|---|
| `notification.servicio.suspendido` | al pasar a `suspendido` | `NotificationEventListener.onServicioSuspendido()` | WhatsApp al abonado (si `notif_suspension_activa`) |
| | | `OutboxRedService.onServicioSuspendido()` | **encola `SUSPENDER_ONU`** en el outbox |
| `notification.servicio.reactivado` | al pasar a `activo` desde `suspendido` | `NotificationEventListener.onServicioReactivado()` | WhatsApp al abonado |
| | | `OutboxRedService.onServicioReactivado()` | **encola `REACTIVAR_ONU`** en el outbox |

**El hallazgo:** la orden que apaga y enciende la ONU viaja dentro de un evento del namespace
`notification.*`. No hay un evento de dominio «servicio suspendido»: hay un evento de
notificación al que alguien le colgó una consecuencia operativa. Si mañana se desactivan las
notificaciones de ese tipo, el listener de `outbox-red` sigue enganchado al mismo nombre — hoy
funciona porque el filtro `notif_suspension_activa` vive dentro del listener de notificaciones,
no en la emisión.

**No hay evento de baja.** El comentario en `outbox-red.service.ts:270` lo dice: *«Baja
definitiva: se invoca desde contratos.service (no hay evento de baja)»*. Por eso la baja llama
a `encolarDesaprovisionarOnu()` directamente y la suspensión no. Dos caminos distintos para la
misma clase de orden.

**Trabajos BullMQ:** ninguno. `cambiarEstado()` no encola nada en Bull; la asincronía la pone
el outbox propio y `setImmediate`.

## 7. Payload real hacia `comandos_red_pendientes`

Estructura de la tabla: `id · contrato_id · router_id · accion · payload jsonb · intentos ·
max_intentos (12) · estado · ultimo_error · creado_en · ejecutado_en · reclamado_por ·
claim_expira_en`.

Inserción idempotente por naturaleza:

```sql
INSERT INTO comandos_red_pendientes (contrato_id, router_id, accion, payload)
VALUES ($1, $2, $3, $4)
ON CONFLICT (contrato_id, accion) WHERE estado IN ('PENDIENTE','EN_PROCESO') DO NOTHING
```

### Los tres payloads que produce `cambiarEstado()`

**`SUSPENDER`** — solo si el intento directo contra MikroTik falló. Registro real de
producción:

```json
{
  "clienteId":    "0e814d05-4103-4c74-b905-07e40bb79c0a",
  "deudaTotal":   64,
  "ipAsignada":   "172.16.201.2",
  "usuarioPppoe": "pieroescobar"
}
```

**`REACTIVAR`** — mismo disparador, forma idéntica (`ipAsignada`, `usuarioPppoe`, `clienteId`,
`deudaTotal`).

**`DESPROVISIONAR`** — solo si S3 falló durante la baja:

```json
{
  "contratoId":   "<uuid>",
  "ipAsignada":   "172.16.201.2",
  "usuarioPppoe": "pieroescobar",
  "motivo":       "baja_definitiva_hardware_fallo"
}
```

**`SUSPENDER_ONU` / `REACTIVAR_ONU` / `DESAPROVISIONAR_ONU`** — los produce `outbox-red`, no
`cambiarEstado()`. Registro real de producción:

```json
{ "empresaId": "a0000000-0000-0000-0000-000000000001" }
```

### La asimetría del payload

Los comandos de MikroTik son **autocontenidos**: llevan la IP, el usuario PPPoE y el
`router_id`, así que el ejecutor puede aplicarlos sin volver a consultar nada. Los comandos de
ONU llevan **solo el `empresaId`**, con `router_id = NULL`: la OLT, el frame/slot/puerto, el
`onu_id` y el serial se resuelven en tiempo de ejecución leyendo `ftth_onu_registro`.

Eso significa que un comando de ONU **no es reproducible**: si el registro cambia entre el
encolado y la ejecución, el comando hace algo distinto de lo que se pidió. Y no es portable —
no se puede reejecutar en otra instalación ni auditar qué se ordenó exactamente.

## 8. Resumen para el cuadro de decisión

| Flecha | ¿Core? | Tipo | ¿Cruza propiedad? | ¿Se espera? | ¿Qué pasa si falla? | ¿Idempotente? |
|---|---|---|---|---|---|---|
| → `servicios` | sí | comando | no | sí | excepción, aborta | sí (mismo `upd`) |
| → `servicios_historial` | sí | comando | no | sí | excepción tras haber cambiado el estado | **no** (inserta duplicado) |
| → `clientes` | sí | comando | **sí** | sí | `warn`, sigue | sí (condicionado por `WHERE estado = …`) |
| → `clientes_historial_estados` | sí | comando | **sí** | sí | `warn`, sigue | **no** |
| → `ips_asignadas` | sí | comando | **sí** | sí | paso `FAIL` en la saga, sigue | sí |
| → `auditoria_logs` | sí | comando | no | sí | excepción | **no** |
| → `saga_log` | no | comando | no | sí | ignorado | **no** |
| → MikroTik (firewall/PPPoE) | no | comando | no | **no** | `warn` + outbox | sí (address-list y secret son declarativos) |
| → IPTV (xui) | no | comando | no | **no** | `warn`, se pierde | sí |
| → OLT (SmartOLT, solo baja) | no | comando | no | sí, 20 s | paso `FAIL`, sigue | sí |
| → outbox (`comandos_red_pendientes`) | no | comando diferido | **sí** | sí | `error` logueado | sí (`ON CONFLICT DO NOTHING`) |
| → evento `notification.*` | no | evento | no | **no** | se pierde en silencio | depende del consumidor |
| ← `DeudaPorContratoService` | sí | consulta | no | sí | excepción | n/a |

### Las cuatro cosas que un diseño nuevo tiene que resolver

1. **No hay transacción.** Nueve tablas, autocommit una por una. Un fallo entre el paso 3 y el
   4 deja el servicio con el estado cambiado y sin historial.
2. **El resultado no distingue aplicado de aceptado.** Devuelve `Contrato`; el estado del
   hardware no está en él y no puede estarlo, porque el hardware se toca fuera del request.
3. **La máquina de estados solo gobierna al humano.** `automatico = true` la desactiva entera,
   guardas incluidas, y lo usan cinco llamadores.
4. **La orden a la ONU viaja en un evento de notificación.** El único canal que conecta el
   cambio de estado comercial con la OLT es `notification.servicio.suspendido`.
