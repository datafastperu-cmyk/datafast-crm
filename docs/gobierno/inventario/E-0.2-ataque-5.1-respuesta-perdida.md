# Ataque 5.1 — «el proveedor aplica, pero la respuesta se pierde»

Levantado el 2026-08-11 sobre el código y la base de producción.

---

## Resumen ejecutivo

`indeterminado` existe, está bien documentado, y el outbox lo trata correctamente cuando lo
recibe. **Pero ninguna operación real contra la OLT puede producirlo.**

Los métodos de hardware (`suspender`, `rehabilitar`, `desaprovisionar`, `actualizarWan`,
`reaplicar`) **capturan la excepción del timeout dentro de sí mismos** y la convierten en
`{ exitoso: false }`. El envoltorio `*PorContrato()` traduce ese `false` a
`{ clase: 'reintentable' }`. `clasificarError()` —la única función que convierte un timeout en
`indeterminado`— vive en un `catch` exterior al que el `catch` interior nunca deja llegar nada.

```typescript
// provision-ftth.service.ts:2311 — suspenderPorContrato
try {
  const r = await this.suspender(...);        // ← este método ya capturó el timeout dentro
  return r.exitoso
    ? { clase: 'aplicado',     mensaje: r.mensaje }
    : { clase: 'reintentable', motivo:  r.error ?? r.mensaje };   // ← el timeout cae AQUÍ
} catch (err) {
  return clasificarError(err);                 // ← inalcanzable para un timeout de hardware
}
```

```typescript
// provision-ftth.service.ts:2531 — suspender
try {
  const res = await this.automation.ftthSuspendOnu({...});
  exitoso = res.success;
} catch (err: any) {
  error = err.message;                         // ← el timeout muere aquí
  this.logger.error(`FTTH suspender SSH falló | ...`);
}
if (!exitoso) return { exitoso: false, mensaje: '...', error };
```

Consecuencia: **un timeout contra la OLT se clasifica `reintentable` y se reintenta a ciegas.**
Es exactamente lo que la regla escrita prohíbe.

En MikroTik la situación es más simple y peor: **no hay clasificación en absoluto.** Todo
error —incluido el timeout— hace `intentos + 1` y vuelve a `PENDIENTE`.

**Nunca se ha probado.** No hay ni un test que ejercite la ruta indeterminada del outbox ni de
`olt-nativo`. Los tres ficheros que mencionan `indeterminado` son
`resultado-operacion.spec.ts` (prueba `clasificarError` aislada), `contrato-adaptador.spec.ts`
(pagos) y `crm-nativo.aislamiento.spec.ts` (WhatsApp).

El único sitio donde hoy se reconoce «pudo haberse aplicado» es el barrido de reclamos
expirados — es decir, cuando **muere el proceso**, no cuando **el proveedor no contesta**.

# ATAQUE 5.1 — DATOS REALES · Operación A (MikroTik)

**Operación:** `SUSPENDER`
**Proveedor:** MikroTik RouterOS vía API nativa (pool de conexiones), a través del túnel VPN

**Registro real, íntegro** (`comandos_red_pendientes` id=49):

```json
{
  "id": 49,
  "contrato_id": "92534c84-8498-48be-9371-7e34230eb2ae",
  "router_id":   "8aaefb51-2dbb-4582-a744-a8f8cf880fcf",
  "accion":      "SUSPENDER",
  "payload": {
    "clienteId":    "0e814d05-4103-4c74-b905-07e40bb79c0a",
    "deudaTotal":   64,
    "ipAsignada":   "172.16.201.2",
    "usuarioPppoe": "pieroescobar"
  },
  "intentos":        0,
  "max_intentos":    12,
  "estado":          "EJECUTADO",
  "ultimo_error":    null,
  "creado_en":       "2026-08-05T13:00:01.688Z",
  "reclamado_por":   "0:2603023",
  "reclamado_en":    "2026-08-05T13:00:01.800Z",
  "claim_expira_en": "2026-08-05T13:10:01.800Z",
  "ejecutado_en":    "2026-08-05T13:00:02.815Z"
}
```

Del encolado a la ejecución: **1,127 s**. Reclamo tomado 112 ms después de insertar.

**Flujo:**

1. `ContratosService.cambiarEstado(SUSPENDIDO)` intenta MikroTik directo en `setImmediate`.
   Falla → `outboxRed.encolar('SUSPENDER', ...)` → `INSERT ... ON CONFLICT (contrato_id, accion)
   WHERE estado IN ('PENDIENTE','EN_PROCESO') DO NOTHING`.
2. `procesarPendientes()` reclama en bloque: `UPDATE ... SET estado='EN_PROCESO',
   reclamado_por=$dueño, claim_expira_en=NOW()+600s WHERE id IN (SELECT ... WHERE
   estado='PENDIENTE' ORDER BY creado_en LIMIT 10 FOR UPDATE SKIP LOCKED)`.
3. Lee `routers` por `router_id`. Si no existe → `AGOTADO` ('Router eliminado de BD').
4. `firewallSvc.suspenderCliente()` → `pppoeSvc.desconectarSesion()` → `pppoeSvc.setEstado(true)`.
5. Si ninguno lanzó → `estado='EJECUTADO', ejecutado_en=NOW()`.

**Si hay timeout:**
→ El adaptador **lanza**. El `catch` de `ejecutarComando` hace:
```sql
UPDATE comandos_red_pendientes
SET estado='PENDIENTE', intentos = intentos+1, ultimo_error = <mensaje>,
    reclamado_por=NULL, reclamado_en=NULL, claim_expira_en=NULL
WHERE id = $1
```
Sin clasificar. Sin distinguir «no llegó» de «llegó y no contestó».

**Si el proveedor aplicó pero la respuesta se perdió:**
→ **Datafast no lo sabe y no lo pregunta.** El comando vuelve a `PENDIENTE` y se reejecuta
completo. No hay daño porque las tres operaciones son idempotentes por naturaleza del RouterOS
(`address-list add` sobre una IP ya listada, `secret set disabled=yes` sobre un secret ya
deshabilitado), pero **es una idempotencia heredada del proveedor, no una garantía del ERP**.
El caso peligroso es `DESPROVISIONAR`, que hace `pppoeSvc.eliminar()`: si el `remove` se aplicó
y la respuesta se perdió, el reintento encuentra `secrets.length === 0` y **retorna `void` en
silencio** — indistinguible de un éxito y de un fallo.

**Reintento:**
→ Ilimitado. `max_intentos = 12` **no detiene nada**: al llegar a 12 solo emite
`notification.outbox_red.agotado` y registra un evento de sistema; el comando sigue en
`PENDIENTE` y se reintenta indefinidamente. Cadencia: cron cada 5 min + disparo inmediato en
`notification.router.conectado`. El único estado terminal de fallo es `AGOTADO`, y solo se
alcanza si el router ya no existe en la base.

**ResultadoOperacion:**
→ **No se usa.** La rama MikroTik del outbox no lo conoce. Los adaptadores devuelven
`Promise<void>` o `Promise<string>`.

**Consulta de estado posterior:**
→ Existe: `ContratosService.verificarProvisionHardware()` — 3 intentos × 2 s, consulta
`/ppp/secret/print?name=<usuario>` o `/ip/arp/print?address=<ip>`, devuelve `boolean`.

**Quién la ejecuta:**
→ **Solo `activar()`**, en el paso S3b del alta. Escribe `servicios.hardware_verificado` y
`hardware_estado`. **El outbox nunca la llama.** Tras un timeout en un `SUSPENDER` nadie
comprueba si el secret quedó deshabilitado.

# ATAQUE 5.1 — DATOS REALES · Operación B (OLT)

**Operación:** `SUSPENDER_ONU`
**Proveedor:** Huawei MA5800 vía `olt-automation-service` (HTTP → paramiko → SSH → CLI)

**Registro real** (`comandos_red_pendientes` id=34, `REACTIVAR_ONU`, misma familia):

```json
{
  "id": 34,
  "accion":          "REACTIVAR_ONU",
  "payload":         { "empresaId": "a0000000-0000-0000-0000-000000000001" },
  "router_id":       null,
  "intentos":        1,
  "max_intentos":    12,
  "estado":          "EJECUTADO",
  "ultimo_error":    null,
  "creado_en":       "2026-07-29T17:10:31.005Z",
  "reclamado_por":   "0:1259433",
  "reclamado_en":    "2026-07-29T17:15:00.282Z",
  "claim_expira_en": "2026-07-29T17:25:00.282Z",
  "ejecutado_en":    "2026-07-29T17:15:08.925Z"
}
```

El payload lleva **solo el `empresaId`**. OLT, slot, puerto, `onu_id`, SN y `service_port_id`
se resuelven en ejecución leyendo `ftth_onu_registro`. El comando **no es reproducible**: si el
registro cambia entre el encolado y la ejecución, se ejecuta otra cosa.

Peor caso documentado (id=9, `REAPROVISIONAR_ONU`): **16 intentos sobre un `max_intentos` de
12**, 49 minutos entre encolado y ejecución, `ultimo_error = "Otro proceso ya está
aprovisionando este contrato"` — un 409 de lock propio, reintentado 16 veces.

**Flujo:**

1. `ContratosService.cambiarEstado(SUSPENDIDO)` emite `notification.servicio.suspendido`.
2. `OutboxRedService.onServicioSuspendido()` → `encolarOnu('SUSPENDER_ONU', ...)`, que primero
   comprueba que exista `ftth_onu_registro` vivo (si no, no encola nada) y luego dispara
   `procesarPendientes()` inmediato.
3. Reclamo atómico idéntico al de MikroTik.
4. `ejecutarComandoOnu()` → `ftthSvc.suspenderPorContrato(contratoId, empresaId)`.
5. Éste consulta la máquina de estados (`evaluarTransicion`) — de ahí salen `ya_en_destino` y
   `no_aplica` sin tocar el hardware — y si procede llama a `suspender()` → HTTP al
   microservicio → SSH → `ont deactivate` + baja del service-port.

**Si hay timeout:**
→ El cliente HTTP lanza. `suspender()` lo **captura dentro** (`catch (err) { error = err.message }`)
y devuelve `{ exitoso: false, error }`. `suspenderPorContrato()` lo traduce a
`{ clase: 'reintentable' }`. El outbox hace `intentos+1`, `estado='PENDIENTE'`, libera el
reclamo. **Reintento a ciegas.**

**Si el proveedor aplicó pero la respuesta se perdió:**
→ **Datafast asume que no pasó nada y reintenta.** La segunda vez `evaluarTransicion('suspender',
'activo')` — pero el registro sigue en `activo` porque el `UPDATE` a `SUSPENDIDO` solo ocurre
*después* de un `exitoso: true`. Así que reintenta el `ont deactivate` sobre una ONU ya
desactivada. En este caso concreto el MA5800 lo tolera; en `desaprovisionar` (que borra el
`ont` y libera el service-port) el reintento sobre un recurso ya eliminado es lo que produjo
las 1 788 llamadas del incidente del 24/07.

Hay una salvaguarda parcial y solo para el desaprovisionamiento: la Regla C revalida el estado
vivo del contrato antes de ejecutar la tumba, y devuelve `no_aplica` si el contrato se reactivó
mientras tanto.

**Reintento:**
→ Igual que MikroTik: ilimitado, `max_intentos = 12` solo notifica. El caso id=9 lo demuestra
con 16 intentos registrados.

**ResultadoOperacion:**
→ **Sí se usa**, y el outbox lo trata bien: `aplicado`/`ya_en_destino`/`no_aplica` → `EJECUTADO`;
`rechazado_definitivo` → `AGOTADO` + evento; `indeterminado` → `PENDIENTE` + evento
`OUTBOX_ONU_INDETERMINADO` sin bucle inmediato; `reintentable` → `PENDIENTE`.
**El problema no es el outbox: es que `indeterminado` nunca llega.**

**Consulta de estado posterior:**
→ Existen varias, y buenas: `ftthPollOnline` (espera a que la ONU aparezca tras el alta),
`ftthCheckWan` (confirma la WAN materializada), `ftthCheckMgmtIp` (carril TR-069),
`verificarYRepararWanDrift` (cron), `reconciliar`, `adoptarOnusHuerfanas`,
`leerOntEstadoOlt` (lectura viva por SSH).

**Quién la ejecuta:**
→ El propio `provisionarFtth()` durante el alta, y los crons de `olt-nativo`
(`ftth-verificar-wan`, `ftth-adoptar-huerfanas`, `ftth-reintentar-rollbacks`,
`reconciliador-ftth-onu`). **El outbox no llama a ninguna de ellas tras un fallo.** La
verificación existe pero no está enganchada al camino que la necesita.

## §3 — Qué devuelve realmente cada adaptador

### MikroTik (`pppoe.service.ts`)

| Método | Firma | Éxito | Error | Timeout | Conexión perdida tras enviar |
|---|---|---|---|---|---|
| `crear()` | `Promise<string>` | id del secret | **lanza** | **lanza** | **lanza** |
| `setEstado()` | `Promise<void>` | `undefined` | **lanza** | **lanza** | **lanza** |
| `desconectarSesion()` | `Promise<void>` | `undefined` | **lanza** | **lanza** | **lanza** |
| `eliminar()` | `Promise<void>` | `undefined` | **lanza** | **lanza** | **lanza** |

Los cuatro casos de fallo son **el mismo valor**: una excepción cuyo `message` es lo único que
los distingue. Y hay dos no-op silenciosos:

```typescript
// setEstado
const secrets = await api.write('/ppp/secret/print', [`?name=${name}`]);
if (secrets.length === 0) return;          // ← el secret no existe: retorna igual que si hubiera funcionado

// desconectarSesion
const sessions = await api.write('/ppp/active/print', [`?name=${name}`]);
for (const session of sessions) { ... }    // ← cero sesiones: no hace nada y no lo dice
```

Suspender a un abonado cuyo secret PPPoE no existe en el router devuelve exactamente lo mismo
que suspenderlo con éxito.

### OLT (`provision-ftth.service.ts`)

| Capa | Firma | Timeout / SSH perdido |
|---|---|---|
| `OltAutomationClient.ftthSuspendOnu()` | `Promise<PythonOntSuspendResponse>` | **lanza** (503/422/timeout HTTP) |
| `suspender()` | `Promise<{exitoso, mensaje, error?}>` | **captura** → `{exitoso:false, error}` |
| `suspenderPorContrato()` | `Promise<ResultadoOperacion>` | **`reintentable`** ← el defecto |
| `clasificarError()` | `ResultadoOperacion` | `indeterminado` si `/timeout\|tiempo de espera/i` |

La regla existe, la función existe, el consumidor existe. Falta un único eslabón: que el
timeout llegue hasta `clasificarError`.

### XUI / IPTV

Es **el único proveedor que hoy recupera de una respuesta perdida**, y lo hace casi por
accidente. `XuiLinesService.intentarSincronizarCreacion()` captura el `ConflictException` de
usuario duplicado y busca la línea por nombre antes de rendirse:

```typescript
catch (err) {
  if (err instanceof ConflictException) {
    const existenteRemoto = await this.xuiApi.buscarLinePorUsuario(line.usuario);
    if (existenteRemoto) remoto = existenteRemoto;   // ← «ya se había creado»: se adopta
    else throw err;
  } else throw err;
}
```

Ante un **timeout** no hace eso: la línea queda `PENDIENTE` y el reconciliador reintenta
`crearLine`, que la segunda vez devuelve 409 y entonces sí entra por la rama de arriba. Converge,
pero por el camino largo y sin nombrar nunca el estado indeterminado.

## §5 — Verificación del estado físico, por proveedor

| | ¿Existe consulta? | Quién la ejecuta | Qué devuelve |
|---|---|---|---|
| **MikroTik** | Sí — `verificarProvisionHardware()`: `/ppp/secret/print?name=` o `/ip/arp/print?address=`, 3×2 s | Solo `ContratosService.activar()` (S3b) | `boolean`. Escribe `servicios.hardware_verificado` / `hardware_estado` |
| **OLT** | Sí, varias — `ftthPollOnline`, `ftthCheckWan`, `ftthCheckMgmtIp`, `leerOntEstadoOlt`, `verificarYRepararWanDrift` | `provisionarFtth()` durante el alta; crons de `olt-nativo` y el reconciliador | Estado real de la ONU, de la WAN y del IP de gestión |
| **XUI** | Sí — `getLine(id)`, `buscarLinePorUsuario(username)` | `XuiMonitorService` (drift, ~10 min) y la rama de colisión de `intentarSincronizarCreacion()` | Objeto remoto o `null` |

**Los tres tienen consulta de estado. Ninguno de los tres la usa desde el outbox tras un
fallo.** La verificación está construida y colgada de otro sitio.

## Lo que Ataque 5.1 debe atacar

1. **El timeout no llega al clasificador.** Es un `catch` de más en `suspender()`,
   `rehabilitar()`, `desaprovisionar()`, `actualizarWan()` y `reaplicar()`. Cinco métodos.
2. **MikroTik no clasifica nada.** Todo error es el mismo error.
3. **`max_intentos` no limita.** 12 es un umbral de aviso; el reintento es infinito. Hay un
   registro real con 16.
4. **Nadie verifica antes de reintentar.** Las sondas existen para los tres proveedores y
   ninguna está enganchada al reintento.
5. **Nunca se ha probado.** No hay un solo test de la ruta indeterminada en `outbox-red` ni en
   `olt-nativo`.
6. **Detalle menor:** la rama de éxito no limpia `reclamado_por` / `claim_expira_en`, así que
   hay filas `EJECUTADO` con reclamo puesto. Inofensivo hoy (el barrido solo mira
   `EN_PROCESO`), pero hace ilegible el histórico.
