## 1. Flujo real de alta

```
ClienteWizard  (frontend)
     │
     ▼
POST /clientes/onboarding                    ClientesController.onboarding
     │
     ├─ 1. ClientesService.create()          ── ESCRIBE clientes
     │        └─ emitirBienvenidaSiAplica()  ── emite notification.bienvenida
     │
     ├─ 2. saveFacturacionConfig()           ── ESCRIBE cliente_facturacion_config
     │        (ANTES del contrato, a propósito: el comprobante de alta necesita
     │         saber ya si el abonado es prepago y cuál es su día de pago)
     │
     ├─ 3. ContratosService.create()  ─────────────── ver §2
     │        │
     │        ├─ tx: servicios + ips_asignadas
     │        ├─ servicios_historial + auditoria_logs
     │        ├─ emitirComprobanteDeAlta()   ── ESCRIBE facturas
     │        └─ si plan.cuentaIptv → XuiLinesService.crearLineParaContrato()
     │
     ├─ 4. SELECT recalc_tipo_servicio_cliente()   ── función SQL, ESCRIBE clientes
     │
     └─ return { cliente, contrato }         ← el servicio queda PENDIENTE_ACTIVACION
                                               y el cliente PENDIENTE_ACTIVACION

     ⟶ FIN DE LA LLAMADA. Aquí no ha pasado NADA en la red.
```

Después, en **llamadas separadas que el operador dispara a mano**:

```
PATCH /contratos/:id/activar                 ContratosService.activar()
     │
     ├─ S1  provisionarMikrotik()      → MikroTik: secret PPPoE, queue, firewall
     │        (si falla, LANZA y el servicio se queda en PENDIENTE_ACTIVACION)
     ├─ S2  registrarEnAccessListAntena()  → antena AP (soft)
     ├─ S3  ESCRIBE servicios: estado=activo, fecha_instalacion=NOW()
     ├─ S4  verificarProvisionHardware()   → verifica MikroTik, ESCRIBE hardware_*
     ├─      ESCRIBE servicios_historial
     └─ S5  ESCRIBE clientes: estado=activo


POST /olt-nativo/:oltId/ftth/provision       ProvisionFtthService.provisionarFtth()
     │                                       ← FLUJO INDEPENDIENTE. Ver §3.
     └─ el Core no lo invoca, no lo espera y no comprueba que haya ocurrido.
```

### El hallazgo principal de E-0.2-3

**El alta comercial y el aprovisionamiento FTTH son dos flujos que no se conocen.**

- `activar()` provisiona **MikroTik** y marca el servicio como instalado. No llama a
  `olt-nativo` ni consulta si existe una ONU.
- `provisionarFtth()` entra por su propia URL, con su propio permiso (`onu:provision`), y
  recibe del operador los 17 campos de la ONU.
- Ninguno de los dos verifica al otro. No hay orden obligado entre ellos.

En el caso real (§6) eso produjo un servicio FTTH **activo, instalado y facturado seis horas
y cuarenta y cinco minutos antes de que su ONU existiera**.

## 2. `ContratosService.create()` en detalle

`contratos.service.ts:118-346` · devuelve `Promise<Contrato>`.

### Qué valida antes de tocar nada

| Validación | Fuente | Si falla |
|---|---|---|
| Plan existe y está activo | `PlanesService.findOne()` | `BadRequestException` |
| MAC no duplicada | SQL sobre `servicios` | `ConflictException` |
| Router existe | SQL sobre `routers` | `BadRequestException` |
| Amarre IP/MAC exige MAC | DTO | `BadRequestException` |
| Segmento pertenece al router | SQL sobre `segmentos_ipv4` | `BadRequestException` |
| La subred existe en el router | `verificarSubredEnRouter()` → **MikroTik en vivo** | `BadRequestException` |

La última es una llamada al hardware **dentro de una validación de alta comercial**.

### La transacción

Es lo mejor construido de todo el flujo: un `QueryRunner` explícito con bloqueo pesimista.

```
BEGIN
  ├─ SELECT ... FOR UPDATE sobre segmentos_ipv4     ← serializa el pool entre instancias PM2
  ├─ calcularNextIpDesdePool()  ó  valida ipManual
  ├─ generarNumeroContrato()    ← advisory lock de transacción, por (empresa, año)
  ├─ COUNT servicios del cliente → sufijo del usuario PPPoE   ← bajo el MISMO lock
  ├─ comprueba que el usuario PPPoE no exista
  ├─ INSERT servicios
  └─ INSERT ips_asignadas
COMMIT      ← si algo falla, el rollback libera la IP automáticamente
```

### Qué genera

| Dato | Cómo se genera | Dónde queda |
|---|---|---|
| `numero_contrato` | correlativo por empresa y año, bajo advisory lock | `servicios` |
| `usuario_pppoe` | `cli_<8 hex del clienteId>` + sufijo si el cliente ya tiene servicios | `servicios` |
| `password_pppoe` | aleatorio de 12 caracteres, cifrado (si el cifrado falla, **se guarda en claro**) | `servicios` |
| `ip_asignada` | siguiente libre del pool del segmento, o la IP manual | `servicios` + `ips_asignadas` |
| `estado` | siempre `PENDIENTE_ACTIVACION` | `servicios` |
| `precio_mensual` | `dto.precioMensual ?? plan.precio` — **copia** | `servicios` |
| `dia_facturacion` | `dto.diaFacturacion ?? config app.billing.day` | `servicios` |
| `dias_prorroga` | `dto.diasProrroga ?? 3` | `servicios` |

### Qué escribe, en orden

```
create()
│
├─ [tx] INSERT servicios                        ← el servicio
├─ [tx] INSERT ips_asignadas                    ← la IP (tabla ajena, dueño mikrotik)
│  COMMIT
│
├─ INSERT servicios_historial                   ← post-commit, fuera de la tx
├─ INSERT auditoria_logs                        ← post-commit
├─ UPDATE clientes SET nota_baja = NULL         ← tabla ajena
├─ UPDATE clientes → readmisión si venía de baja_definitiva   ← tabla ajena
│     └─ INSERT clientes_historial_estados      ← tabla ajena
│
├─ emitirComprobanteDeAlta()
│     ├─ PoliticaFacturacionService.resolver()  ── LEE config del cliente
│     ├─ proximoVencimiento() + periodoServicio()
│     └─ FacturacionService.create()            ── ESCRIBE facturas
│           · prepago → ítem de mensualidad al precio DEL CONTRATO (no del plan)
│           · costoInstalacion > 0 → ítem de instalación
│           · postpago sin instalación → NO emite nada
│           · si falla: NO relanza; log + auditoría «emitirlo a mano»
│
└─ si plan.cuentaIptv → setImmediate(XuiLinesService.crearLineParaContrato())
                                                ── ESCRIBE xui_lines (sin esperar)
```

**Tablas escritas (7):** `servicios`, `ips_asignadas`, `servicios_historial`,
`auditoria_logs`, `clientes`, `clientes_historial_estados`, `facturas` (+ `xui_lines`
asíncrono).

### Módulos que llama

| Módulo | Qué le pide | Naturaleza |
|---|---|---|
| `planes` | `findOne()` | consulta |
| `mikrotik` | `verificarSubredEnRouter()` | **consulta al hardware en vivo** |
| `facturacion` | `PoliticaFacturacionService.resolver()`, `FacturacionService.create()` | consulta + comando |
| `auth` | `AuditoriaService.logCreate()` | comando |
| `xui` (IPTV) | `crearLineParaContrato()` | comando, sin esperar |

**No llama a `olt-nativo`. No llama a `planta-externa`. No llama a `outbox-red`.**

### Qué NO hace

- **No toca la OLT ni la ONU.** Un servicio `tipo_servicio = 'ftth'` se crea igual que uno WISP.
- **No reserva puerto NAP** ni crea acometida.
- **No configura MikroTik.** Solo lo consulta. La configuración es de `activar()`.
- **No pone el servicio en producción.** Queda `PENDIENTE_ACTIVACION`.

## 3. Aprovisionamiento FTTH y su relación con el alta

```
ModalProvisionFtth  (frontend)
     ▼
POST /olt-nativo/:oltId/ftth/provision      permiso: onu:provision
     ▼
ProvisionFtthService.provisionarFtth(oltId, empresaId, dto)
     ├─ FtthOperacionLockService.conLock(contratoId, 'provision')
     ├─ _provisionarFtthInterno()
     │    ├─ valida el contrato                    ── LEE servicios
     │    ├─ OltServicePortPoolService.allocar()    ── ESCRIBE olt_service_port_pool
     │    ├─ OltOnuIdPoolService.allocar()          ── ESCRIBE olt_onu_id_pool
     │    ├─ OperacionWizardPasoService.registrarIntencion()  ← write-ahead
     │    ├─ automation.ftthProvisionGpon()         ── HTTP → olt-automation-service → SSH → OLT
     │    ├─ automation.ftthPollOnline()            ── espera a que la ONU aparezca
     │    ├─ _buildWanInject() + ftthInjectWanPppoe()  ── OMCI: WAN de la ONU
     │    ├─ _aplicarPresetAuto()                   ── ESCRIBE contrato_onu_config (SSID, WiFi)
     │    ├─ _ensureCarrilGestion()                 ── carril TR-069
     │    ├─ _syncVlanContrato()                    ── ESCRIBE servicios (¡tabla del Core!)
     │    └─ ESCRIBE ftth_onu_registro
     └─ si pendienteCarrilTr069 → emit 'ftth.carril.activar' → outbox-red
```

### De dónde sale cada dato que llega a la OLT

Payload real de `ftthProvisionGpon` (`PythonFtthGponRequest`):

| Campo hacia la OLT | Origen | ¿Quién decide? |
|---|---|---|
| `connection` (IP, usuario, clave, puerto) | `olt_dispositivos` por `oltId` de la URL | ERP |
| `frame` | **DTO — lo teclea el operador** | operador |
| `slot` | **DTO — lo teclea el operador** | operador |
| `port` (PON) | **DTO — lo teclea el operador** | operador |
| `sn` (SN de la ONU) | **DTO — lo teclea o escanea el operador** | operador |
| `vlan` | **DTO** | operador |
| `lineprofile_id` | **DTO** | operador |
| `srvprofile_id` | **DTO** | operador |
| `traffic_index_down` / `_up` | **DTO**, opcional; `null` = sin límite | operador |
| `onu_id` | DTO opcional; si falta, `OltOnuIdPoolService.allocar()` | **ERP** |
| `service_port_id` | DTO opcional; si falta, `OltServicePortPoolService.allocar()` | **ERP** |
| `description` | `dto.description ?? servicios.numero_contrato`, con sello `DATAFAST_` | ERP |
| `wanMode` | DTO, `'bridge'` o `'routing'` | operador |

Y en la segunda fase, `ftthInjectWanPppoe` (`_buildWanInject`), según `servicios.tipo_auth`:

| `tipo_auth` | Modo WAN | Datos que cruzan | Origen |
|---|---|---|---|
| `pppoe` | `mode: 'pppoe'` | `username`, `password` (descifrada) | **`servicios`** — los generó `create()` |
| `amarre_ip_mac` | `mode: 'static'` | `ip_address`, `mask`, `gateway`, `pri_dns` | `servicios` + `segmentos_ipv4` |
| `amarre_ip_mac_dhcp` | `mode: 'dhcp'` | — | — |

**Ahí está la única costura real entre el alta y la OLT:** el usuario y la clave PPPoE que
`create()` generó dentro de su transacción se leen desde `servicios` en el momento de inyectar
la WAN. Es una lectura directa de la tabla del Core desde el módulo técnico — no un contrato,
no un payload, no un evento.

**De los 13 datos que llegan a la OLT, 8 los teclea el operador y 5 los deriva el ERP.** El
Core no aporta ninguno excepto el número de contrato para la descripción y las credenciales
PPPoE.

### La escritura invertida

`_syncVlanContrato()` hace que **`olt-nativo` escriba `servicios`**, la tabla del Core. El
módulo técnico corrige el dato comercial en vez de devolverlo.

## 4. Planta externa

```
Alta FTTH
   │
   ▼
¿Planta participa?        ── NO. En absoluto.
```

Medido, no supuesto:

- `pe_acometida`: **0 filas**.
- Ningún fichero fuera de `src/modules/planta-externa/` invoca a `PlantaExternaService` ni a
  `PlantaExternaPuertosService`. Cero llamadas entrantes.
- `ProvisionFtthService` no menciona NAP, puerto ni acometida en ninguna de sus 2 900 líneas.
- `ContratosService.create()` tampoco.
- La baja (`cambiarEstado(BAJA_DEFINITIVA)`) **no libera el puerto NAP**, porque nunca lo tomó.

Lo llamativo es que el módulo **sí tiene** la API que haría falta, y es la mejor diseñada del
ERP: `reservarPuerto()`, `asignarPuerto()`, `liberarPuerto()`, `extenderReserva()` — las cuatro
devuelven `ResultadoOperacion`. Son 4 de las 11 operaciones de todo el ERP que hablan el
vocabulario de dominio.

Es decir: **el contrato existe y nadie lo firma.** No hay que diseñarlo; hay que conectarlo.

Quién debería solicitar, reservar y confirmar no está definido en ninguna parte del código: no
hay flujo implementado, ni siquiera parcial.

## 5. Plan → Servicio → Contrato

### La cadena real

```
planes                    ← catálogo comercial (nombre, producto, velocidad, precio, perfiles)
   │  plan_id (FK, RESTRICT)
   ▼
servicios                 ← la instancia: este plan, para este cliente, en esta dirección
   │  contrato_id (FK, RESTRICT)
   ▼
contratos                 ← el ACUERDO: cliente + número + fecha de inicio. 9 columnas.
```

**Ojo con la dirección.** El «contrato» comercial (`contratos`) es el **padre** del servicio,
no su consecuencia. Un acuerdo agrupa N servicios. La tabla se creó en la fase 3b y hoy tiene
**9 columnas, ninguna entidad TypeORM y ningún escritor en el código**: la pobló la migración.

### Qué se copia y qué se consulta

| Dato | ¿Copia o referencia? | Dónde vive | Consecuencia |
|---|---|---|---|
| **Precio** | **COPIA** al crear (`precioMensual = dto.precioMensual ?? plan.precio`) | `servicios.precio_mensual` | Subir el precio del plan **no** afecta a los servicios ya dados de alta. Es lo correcto: ahí vive el descuento pactado. |
| **Velocidad bajada/subida** | **REFERENCIA** — se lee del plan en cada provisión | `planes.velocidad_bajada/_subida` | Cambiar el plan **sí** cambia la velocidad del abonado, en la siguiente reprovisión |
| **Perfil PPPoE** | **REFERENCIA** (`planes.ppp_profile`) | `planes` | ídem |
| **`crear_reglas_en_router`** | **REFERENCIA** | `planes` | ídem |
| **Cuenta IPTV** | **REFERENCIA**, leída solo una vez en `create()` | `planes.cuenta_iptv` | Activar IPTV en el plan **no** crea líneas para los abonados existentes |
| **Nombre del plan** | **COPIA** al comprobante (descripción del ítem) | `facturas.items` | correcto: el comprobante congela lo facturado |

**Dos criterios distintos en la misma alta.** El precio se congela; la velocidad se consulta
viva. Ninguna de las dos decisiones está escrita en ningún sitio: se deduce de dónde se leyó
el dato.

La consulta de velocidad ocurre en `provisionarMikrotik()`, con un `JOIN` directo a `planes`
desde el módulo `contratos`:

```sql
SELECT ... pl.ppp_profile, pl.velocidad_bajada, pl.velocidad_subida, pl.crear_reglas_en_router
FROM servicios co
JOIN clientes cl ON cl.id = co.cliente_id
LEFT JOIN routers ro ON ro.id = co.router_id
LEFT JOIN planes  pl ON pl.id = co.plan_id
```

Cuatro tablas de cuatro dominios distintos en una consulta escrita por el Core.

   existía; el dato del plan es decorativo.
5. **«Antena AP: ERROR» no impidió activar.** Es un paso `SKIPPED` en la saga y una advertencia
   en el historial. Nadie lo recogió después.
6. **Los comprobantes apuntan al acuerdo, no al servicio.** Los dos tienen `servicio_id` NULL y
   `contrato_id` poblado. Con un cliente de un solo servicio es equivalente; con dos, no.

## 7. La respuesta a la pregunta de E-0.2-3

> ¿Quién inicia el alta, quién decide qué se contrata, quién crea la instancia comercial,
> quién solicita los recursos técnicos y quién ejecuta cada recurso?

| Pregunta | Hoy |
|---|---|
| ¿Quién inicia? | El operador, desde tres pantallas distintas y en tres llamadas HTTP separadas |
| ¿Quién decide qué se contrata? | El operador elige el plan; el Core copia el precio |
| ¿Quién crea la instancia comercial? | `ContratosService.create()` — bien, con transacción |
| ¿Quién solicita la IP? | **El Core**, de su propio pool, dentro de su transacción |
| ¿Quién solicita el PPPoE? | **El Core** lo genera; MikroTik solo lo materializa |
| ¿Quién solicita el puerto NAP? | **Nadie** |
| ¿Quién solicita la ONU? | **El operador**, tecleando 8 parámetros GPON |
| ¿Quién solicita IPTV? | **El Core**, a partir de un flag del plan, en `setImmediate` |
| ¿Quién ejecuta MikroTik? | El Core, con el pool de conexiones inyectado en su propio servicio |
| ¿Quién ejecuta la OLT? | `olt-nativo` → `olt-automation-service` → SSH |
| ¿Quién sabe si todo salió bien? | **Nadie.** No hay punto donde converjan las tres ramas |

### El «Core Dios» ya existe, en parte

`ContratosService` inyecta **14 servicios** en su constructor, entre ellos:

```
WirelessService · PppoeService · ArpService · FirewallService · MikrotikService
RouterConnectionPool · SmartoltApiService · XuiLinesService
```

`RouterConnectionPool` es el **pool de conexiones al MikroTik**, inyectado directamente en el
servicio de contratos. El Core no le pide a Network que haga algo: el Core abre la sesión.

Contra eso, la parte que **no** invadió: la OLT. `contratos` no llama a `olt-nativo` ni una vez
— pero no por diseño, sino porque el aprovisionamiento FTTH nunca se conectó al alta. El
resultado es el opuesto del que se busca: no es autonomía, es desconexión.

### Lo que E-0.2 tiene que resolver, por orden de daño

1. **No existe la intención.** El Core nunca dice «quiero un acceso FTTH para este servicio».
   Dice «actívalo» (MikroTik) y alguien, por separado, teclea una ONU.
2. **No existe la convergencia.** Ninguna operación reúne los resultados de Network, OLT y
   Planta. `activar()` acaba sin saber si hay ONU; `provisionarFtth()` acaba sin decírselo a
   nadie.
3. **El Core es dueño de recursos técnicos** (IP, usuario PPPoE) y **ejecutor de red** (pool de
   conexiones). Son dos invasiones distintas y hay que separarlas por separado.
4. **Planta externa está desconectada con la API ya hecha.** Es la única de las cuatro que no
   requiere diseñar nada: requiere que alguien la llame.
